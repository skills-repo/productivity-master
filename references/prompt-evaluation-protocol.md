# Prompt 评估与迭代协议（prompt-optimizer 增量方法论）

> 子技能 `prompt-optimizer` 给了能力地图（系统提示/上下文/输出格式/few-shot/评估）。本文档补它**装不下**的部分：
> 怎么用可复现的方式证明「这个 prompt 比那个好」。没有评估协议的优化，只是玄学调参。

## 1. 决策树：输出不稳定时调哪个旋钮？

```
输出波动 / 质量不达标
├─ 是否每次输入不同、缺 few-shot？
│   ├─ 是 → 加 2-3 个覆盖边界的示例（见第 4 节 few-shot 选择）
│   └─ 否 ↓
├─ 是否格式经常不合法（JSON 截断/缺字段）？
│   ├─ 是 → 收紧输出格式约束 + 给 schema + 失败重试一次
│   └─ 否 ↓
├─ 是否长文本被截断 / 关键信息丢失？
│   ├─ 是 → 做上下文预算（第 3 节），或先检索再喂
│   └─ 否 ↓
├─ 是否「答非所问」？
│   ├─ 是 → 重写系统提示的角色与边界，明确「不做什么」
│   └─ 否 ↓
└─ 仍不稳 → 建评估集（第 2 节）量化，别靠感觉
```

**核心原则**：每次只改**一个**变量，对比前后指标。同时改多个 = 不知道谁生效。

## 2. 评估集设计（可复现的前提）

不要拿「我随便试的几个例子」当基准。一个能复用的评估集长这样：

```json
{
  "_comment": "prompt 回归评估集：每条含输入与可接受输出判据。评估脚本只读非'_'键。",
  "cases": [
    {"id": "inv-01", "input": "把这段摘要翻译成英文",
     "expect_contains": ["Summary"], "expect_not": ["你好"]},
    {"id": "fmt-02", "input": "输出合法 JSON",
     "expect_schema": {"type": "object", "required": ["name"]}}
  ]
}
```

评估脚本骨架（纯标准库，可放进本仓库 `scripts/`）：

```python
import json, subprocess, sys

def run_prompt(case, model_cmd):
    out = subprocess.run(model_cmd + [case["input"]], capture_output=True, text=True).stdout
    ok = all(t in out for t in case.get("expect_contains", []))
    ok &= not any(t in out for t in case.get("expect_not", []))
    return ok, out

def main(cases_path, model_cmd):
    cases = json.load(open(cases_path))["cases"]
    passed = sum(1 for c in cases if run_prompt(c, model_cmd)[0])
    print(f"{passed}/{len(cases)} passed")
    sys.exit(0 if passed == len(cases) else 1)
```

> 关键：评估集要**版本化**进仓库。改 prompt 前后都跑同一份集，diff 通过率，这才是「优化」的证据。

## 3. Token 预算决策矩阵

上下文不是越多越好，关键是把有限预算分给高信号内容。

| 场景 | 优先保留 | 该压缩/丢弃 | 做法 |
|------|----------|-------------|------|
| 长文档问答 | 问题相关段落 | 全文 | 先检索/切片再喂 |
| 多轮对话 | 最近 N 轮 + 摘要 | 早期闲聊 | 滚动窗口 + 摘要 |
| 代码生成 | 签名/类型/调用点 | 实现细节 | 只给接口契约 |
| 结构化抽取 | 字段定义 + 示例 | 无关上下文 | 明确 JSON schema |

经验公式：留给「输出」的预算 ≈ 总窗口的 20-30%；其余给「高信号输入」。超长输入先摘要，别硬塞。

## 4. Few-shot 选择原则

| 错误做法 | 正确做法 |
|----------|----------|
| 随机抓示例 | 选覆盖边界/异常输入的示例 |
| 正反例混在一起不标注 | 正负例分开，明确「为什么负例错」 |
| 示例格式与推理格式不一致 | 示例严格复用目标输出格式 |
| 示例过多挤占预算 | 2-3 个高质量 > 10 个凑数 |

```text
示例模板（保持与目标一致）：
### 输入
<一个真实边界 case>
### 输出
<标准答案>
### 说明
<为什么这样答，标注关键约束>
```

## 5. 典型坑与规避

1. **拿训练集当评估集**：评估集必须和评估目标分布一致且未参与调参，否则指标虚高。
2. **只看平均通过率**：盯「最差 case」——上线后出事的永远是长尾。
3. **prompt 越写越长**：超过 ~300 词的指令边际收益骤降，先精简再补示例。
4. **不同模型混用基准**：A 模型调好的 few-shot 换到 B 模型可能反效果，评估要绑定模型版本。
5. **忽略输出格式兜底**：即使约束了 schema，仍要代码侧校验 + 失败重试一次，不要裸信模型。
6. **把系统提示当成文档堆**：系统提示是「行为契约」，不是知识库；知识走检索。

## 6. 迭代记录表（建议进仓库）

| 版本 | 改动 | 通过率前→后 | 最差 case 改善 |
|------|------|-------------|----------------|
| v1 | 初版 | - | - |
| v2 | +2 few-shot | 70%→85% | inv-01 通过 |
| v3 | 收紧 JSON schema | 85%→92% | fmt-02 通过 |

每次迭代 append 一行，证明优化方向正确。没有这张表 = 没有在优化，只是在试。

## 7. 实战：一次完整迭代（可复现记录）

目标：让「抽取订单字段」的 prompt 稳定输出合法 JSON。

```bash
# 0) 准备评估集 eval_orders.json（见第 2 节结构）
# 1) 基线 v1（无 schema 约束）
python3 eval_prompt.py --cases eval_orders.json --prompt prompt_v1.txt
# -> 6/10 passed（4 个 JSON 截断/缺字段）

# 2) v2：在系统提示加 JSON schema + 失败重试一次
python3 eval_prompt.py --cases eval_orders.json --prompt prompt_v2.txt
# -> 9/10 passed（剩 1 个长文本截断）

# 3) v3：长文本先切片再抽（上下文预算法）
python3 eval_prompt.py --cases eval_orders.json --prompt prompt_v3.txt
# -> 10/10 passed
```

结论：v3 相对 v1 通过率 60%→100%，且最差 case（长文本）已解决。把这行写进迭代记录表第 7 节。

## 8. 系统提示结构模板（可复用骨架）

```
# 角色
你是一名 <具体角色>，只做 <范围>，不做 <明确边界>。

# 输入
<用户给什么>

# 处理规则
1. <第一条硬规则>
2. <第二条硬规则>

# 输出格式
<严格 schema / 模板，含字段名与类型>

# 示例（2-3 个，覆盖边界）
### 输入 ...
### 输出 ...

# 失败兜底
若无法满足格式，输出 {"error": "<原因>"}，不要编造。
```

> 这个骨架本身就是 `template-scaffolder` 可以沉淀的「prompt 模板」——把反复出现的提示结构固化，避免每次从零写。

## 9. 上下文预算计算实例

假设窗口 128k token，目标输出约 2k token（~1.5%）：

```
总预算        128000
- 输出预留      -2000  (1.5%)
- 系统提示      -1500  (固定契约)
= 可用输入     124500
```

若单次输入文档 200k token，必须**先检索切片**到 ≤124k，否则截断会丢信号。经验：可用输入里，高信号片段（问题相关/签名/字段定义）应占 ≥70%，噪声（全文/闲聊）压到 <30%。

## 10. 典型坑与规避（续）

7. **评估集太小（<10 条）**：通过率波动大，无法区分「真优化」和「碰巧」，至少 20-30 条且含长尾。
8. **改了评估集又改了 prompt**：变量不唯一，前后对比失效；评估集冻结后才动 prompt。
9. **重试掩盖了根因**：靠重试把通过率刷上去，但单次仍不稳；重试只是兜底，根因要修 prompt。
10. **忽视延迟/成本**：few-shot 加越多越贵越慢，评估要同时记「通过率 / 平均 token / 延迟」三项。
